# Phase 2 — Learners, staff and academic structure

Implemented locally on 7 October 2026. Supabase service integration remains pending because no project is configured. Production screens use Supabase; fixture responses exist only in browser tests.

## Working sequence

1. Sign in as a school administrator and select the school.
2. Open **Academic structure**. Create an academic year, its non-overlapping terms, and your school's grades.
3. Create classes for a particular year and grade. Set an optional maximum enrollment. Year/grade associations cannot be edited later because they define the historical class; create another class when changing that structure.
4. Create subjects. Open a class with **View**, then add its class subjects. Set compulsory/elective status and the configurable subject weight.
5. Open **Staff & teachers**. Add a staff profile and tick **Teaching staff** for teachers. Open a teacher profile and add a teaching assignment to a class subject. Archived assignments and inactive/archived teachers lose learner access.
6. Open **Parents & guardians** and register guardian contact details.
7. Open **Learners**, create a learner, then choose **View**. Add guardian links, including the relationship and optional primary guardian. A guardian may link to multiple learners; a learner may have several guardians but only one active primary guardian.
8. On the learner profile, choose **Enroll learner**, then select an academic year, destination class and start date.
9. For class changes or promotion, choose **Move / promote** on the current enrollment. Enter the previous end date and the new start date. The database closes the previous placement and creates the new placement atomically. Both years remain in the history. Use **Close enrollment** for completion, withdrawal or transfer out.
10. Close active enrollments before archiving a learner or changing their status. Archiving hides active records; it does not delete history. Use the **Archived records** filter to restore records where appropriate.

Records and relation pickers use server-side querying and pages of 20 records. Learners can also be filtered by current class. Directory sorting uses database fields and a stable ID tie-breaker. A record version accompanies updates; another user's edit produces a save error rather than a silent overwrite. Reload before retrying a conflicted change.

## Account links and visibility

An optional **Linked account ID** connects a person record to a Supabase user. The user must already have the matching role in this school: STUDENT for a learner, PARENT for a guardian, TEACHER for a teacher. School administrators manage memberships under **People & access**. Creating/inviting Auth accounts still uses a trusted Supabase administrator workflow; there is no new public signup or invite implementation in Phase 2.

| Role | Phase 2 access |
| --- | --- |
| School administrator | Manage people, academic structure, links, assignments and enrollment |
| Principal | Read school-wide people, structure and enrollment |
| Teacher | Read their staff profile, assigned classes, and learners with active enrollment in those classes |
| Parent | Read their guardian profile, linked children and those children's enrollment/class information |
| Learner | Read their own learner profile and enrollment/class information |
| Accountant/librarian | No learner directory access from these roles alone |

Schools can have multiple memberships and roles. Permissions combine, but database RLS remains authoritative. Teachers cannot read the guardian contact directory through their teaching role. Parent/learner roles cannot change protected records. Global inactive profiles and revoked memberships continue to lose access.

## Database design

Six new migrations create twelve tables: `academic_years`, `terms`, `grades`, `classes`, `subjects`, `students`, `parents`, `staff`, `student_parents`, `class_subjects`, `teacher_assignments` and `enrollments`.

Teaching staff use the `staff` table with `is_teacher`; class and subject assignments are normalized through `teacher_assignments → class_subjects → classes/subjects`. This avoids duplicating a teacher in separate staff and teacher tables. Class subjects are year-specific through their class. Future grade-wide subject templates can populate class subjects without changing this model.

Every tenant relationship uses a composite foreign key including `school_id`. Enrollment additionally ties `(school_id, class_id, academic_year_id)` to a single class. Ordinary users have no DELETE grants. Relationship IDs cannot be changed in place; archive and create another relationship to preserve its history. Enrollment is writable only through checked RPCs. School audit records are generated by database triggers.

Enrollment transactions lock the learner and destination class, validate dates and capacity, reject overlapping placements and check expected versions when moving/closing. Class capacity cannot be reduced below its active enrollment count. Existing terms/enrollments must remain inside any edited academic-year dates, and admission dates cannot be moved past existing enrollment history. Terms cannot overlap within a year. Both PostgreSQL and the browser validate important input constraints.

## Verification and remaining limits

See `VERIFICATION.md` for the executed checks. Embedded PostgreSQL tests execute the actual migrations, grants, RLS and transactional RPCs. Browser tests exercise UI workflows against synthetic responses; they are not evidence of a deployed Supabase service.

The local demo seed now provisions a complete linked example for Phase 2, but could not be run against real Supabase in this environment. Real Auth, PostgREST relationship embedding, API response semantics, hosted migrations and multi-client concurrency still need validation after a project is configured.

Photos/documents, bulk imports/exports, mass promotion, configurable assessment calculations, report cards, attendance, finance and messaging are outside this phase. No mock records are used in production screens and no school data is cached offline. Subject weights here are configuration only; grade calculation belongs to Phase 3.
